# Glossary

Short definitions for terms used throughout the architecture guides.

| Term | Meaning |
|---|---|
| **Architecture** | The significant structures of a system, the relationships between them and the decisions that shape its evolution. |
| **Architectural style** | A set of constraints that shapes how components and connectors are organized. |
| **Bounded context** | A boundary within which a domain model and its terminology have a specific, consistent meaning. |
| **Cohesion** | How closely the responsibilities within a module belong together. |
| **Coupling** | The degree to which one component depends on another component's details or behavior. |
| **Deployment unit** | The artifact or group of artifacts released and operated as one unit. |
| **Event** | A record that something meaningful has happened; it is not a request to perform an action. |
| **Eventual consistency** | A consistency model in which replicas or derived views may temporarily differ but are expected to converge when updates stop. |
| **Module** | A unit of code organization with a defined responsibility and interface. |
| **Modular monolith** | One deployable application organized into modules with explicit boundaries. |
| **Quality attribute** | A measurable property of a system, such as performance, availability, security or maintainability. |
| **Service** | A software component exposed through a contract, often independently deployable in a microservices system. |
| **Trade-off** | A consequence where improving one concern can make another concern harder to achieve. |
| **Architecture Decision Record (ADR)** | A short document that records the context, decision, alternatives and consequences of an architectural choice. |

See [Foundations](fundamentals/index.md) for the concepts behind these terms.
